# Техническое задание (v0.3)
## Десктоп-инструмент офлайн-реконструкции редактируемого фотореалистичного 3D футбольного матча

> **Изменения v0.2 → v0.3.** В тулкит добавлен инструмент **генеративного novel-view (video-diffusion)** — переснятие видео с другого ракурса с сохранением фотореалистичности — с тремя режимами применения: (1) альтернативный рендер-пасс для ограниченных движений камеры; (2) амплификатор данных (синтез доп. ракурсов из одной камеры для подачи в 3D-реконструкцию, моно → псевдо-мульти-вью); (3) генеративный инпейнт невидимых сторон игроков. Введён порт `ViewSynthesizer` и архитектурный шов для него. Обновлены разделы рисков, стека и милстоунов.
>
> **Изменения v0.1 → v0.2.** Зафиксирован объём MVP: один источник, одна точка обзора (мульти-вью вне MVP). Фотореалистичные окружение и аватары — обязательны. Введён принцип **двойной репрезентации** (edit = SMPL + кривые на прокси; render = сплаты/аватары; единый источник истины — SMPL). Милстоуны: M1 — редактируемый цикл, M2 — фотореал-слой. Гексагональная архитектура. Использование — личное/исследовательское, продукт внутренний.

Реал-тайм не требуется: тяжёлые модели выполняются офлайн (локально или через внешние API). Приоритет — качество результата и удобство ручной доводки.

## 1. Назначение и цель

### 1.1 Назначение
PC-приложение (Python), которое из видео/кадров **одной** вещательной камеры строит **фотореалистичную 3D-сцену** футбольного эпизода (поле/стадион, игроки как фотореалистичные анимированные аватары, мяч) с акцентом на **pose estimation**, и даёт инструменты **лёгкого ручного редактирования** результата с **переносом правок на другие кадры**.

### 1.2 Главная цель
Максимально быстро и удобно получить **максимально качественный фотореалистичный 3D** футбольного эпизода, пригодный для дальнейшего редактирования **траекторий мяча, перемещений игроков и поз (вплоть до отдельных костей/частей тела)**.

### 1.3 Зафиксированный объём MVP
| Параметр | Значение |
|---|---|
| Источники / точки обзора | **1 источник, 1 точка обзора** (моно). Мульти-вью — возможное будущее расширение, **не** в MVP. |
| Фотореализм | **Обязателен** (окружение + аватары). Реализуется поэтапно (M1 → M2). |
| Длительность эпизода | до **30 секунд**. |
| Число субъектов | до **24** человек, обычно **≤10**. |
| Назначение | Внутренний инструмент, **личное/исследовательское** использование. |
| Платформа | Desktop, **Python**. |

## 2. Глоссарий

| Термин | Значение |
|---|---|
| **Источник (Source)** | Файл/поток исходного контента (видео или последовательность кадров). В MVP — один. |
| **Сцена (Scene)** | Реконструируемый эпизод: общий мировой фрейм, поле, субъекты, мяч, временной диапазон. |
| **Субъект (Subject)** | Игрок/судья/вратарь — носитель параметрической модели тела (SMPL-X). |
| **SMPL-X** | Параметрическая модель тела (поза θ + форма β), индустриальный стандарт HMR/mocap. |
| **HMR** | Human Mesh Recovery — восстановление 3D-меша/позы человека из изображения/видео. |
| **Гомография (H)** | Преобразование «кадр ↔ плоскость поля»; мировой якорь сцены в моно-режиме. |
| **Двойная репрезентация** | Разделение на **редактируемое** представление (SMPL + кривые на прокси) и **рендер**-представление (сплаты/аватары). Оба приводятся одной SMPL-позой. |
| **Прокси-меш** | Лёгкое тело (SMPL-меш/капсулы) для интерактивного редактирования и переноса правок. |
| **Слой-предложение (Proposal)** | Сырой результат модели; недеструктивная база под правки. |
| **Дельта-коррекция** | Правка оператора, хранимая отдельно (offset / keyframe / constraint). |
| **Рендер-пасс** | Отдельный проход фотореалистичного рендера (сплаты/аватары) из текущего состояния сцены. |
| **Генеративный novel-view (video-diffusion)** | Класс моделей, переснимающих исходное видео с **другой траектории камеры** с сохранением фотореализма (ReCamMaster, TrajectoryCrafter, GCD, GEN3C и др.). Выход — **пиксели/видео**, а не редактируемая геометрия. |
| **ViewSynthesizer (порт)** | Абстракция инструмента генеративного novel-view в тулките; имеет два шва интеграции (рендер-адаптер и амплификатор данных). |

## 3. Целевой пользователь и базовый сценарий

**Пользователь:** технический оператор/художник, понимающий 3D и видео, не обязанный быть ML-инженером.

**Сквозной сценарий (happy path):**
1. Создать проект, добавить источник, задать временные границы эпизода (вручную или через детектор моментов).
2. (Опц.) Прогнать **амплификацию данных** (ViewSynthesizer): из одной камеры синтезировать доп. ракурсы для повышения качества реконструкции.
3. Запустить офлайн-пайплайн реконструкции (очередь задач). Получить сцену со слоями-предложениями на **прокси**-представлении.
4. Проверить качество через **оверлей репроекции** и **карту уверенности**.
5. Точечно поправить: позы/кости проблемных игроков, траекторию мяча, расстановку. Перенести правки на смежные/выбранные кадры.
6. Запустить **рендер-пасс** (фотореал) — сплаты/аватары для произвольной камеры; **либо** ViewSynthesizer для ограниченного облёта вокруг вещательного вида. Проверить.
7. Экспортировать сцену (glTF/USD/FBX/Alembic) и/или веб-просмотрщик (three.js).

## 4. Архитектурное решение

### 4.1 Платформа редактирования: Blender (рекомендация)
Требования «лёгкое 3D-редактирование», «перенос правок на другие кадры», «редактирование траекторий и поз вплоть до частей тела» практически дословно описывают штатный функционал Blender: 3D-вьюпорт с transform-gizmo, мультиселект, **Dope Sheet** и **Graph Editor (F-curves)**, NLA, undo/redo, Python-нативность (`bpy`) и готовый **Meshcapade SMPL-X аддон**.

**Решение:** продукт на базе Blender (расширение/аддон + сервисный слой), тяжёлые задачи — в фоновом воркер-процессе. Альтернативы (гибрид Qt+`bpy`; standalone на PySide6 + свой вьюпорт) документируются с обоснованием отказа: построение гизмо/таймлайна/кривых/undo «с нуля» неоправданно дорого для MVP.

> Лицензии: для внутреннего/исследовательского инструмента ограничения GPL (Blender), AGPL (часть детекторов) и лицензий SMPL некритичны.

### 4.2 Двойная репрезентация (ключевой принцип)
Сцена хранит **два связанных представления**:
- **Редактируемое:** SMPL-X (θ, β, root по кадрам) + кривые (мяч, корневые траектории) на прокси-мешах. Здесь правят и переносят правки.
- **Рендер:** фотореалистичные аватары + 3DGS/NeRF-окружение + текстур-мяч; **либо** видео-выход ViewSynthesizer.
- **Единый источник истины — SMPL-поза и кривые.** Правка автоматически перепроецируется в рендер. **Рендер-представление (включая видео-выход ViewSynthesizer) не редактируется напрямую** — оно производное.

### 4.3 Модели — через адаптеры (self-hosted + внешние API)
Единый интерфейс `ModelProvider`; модели свободно меняются и комбинируются.
- **Self-hosted:** детекция, трекинг, гомография, HMR, трекинг мяча, per-subject аватары.
- **Внешние API (офлайн):** генеративные аватары, генерация/реконструкция окружения, видео-депт, апскейл, **генеративный novel-view (ViewSynthesizer)**. Учитывать стоимость/лимиты/ToS.

### 4.4 Исполнение: офлайн-очередь задач + контентно-адресуемый кэш
- **Job queue:** реконструкция/рендер/амплификация — набор задач по стадиям/сегментам в фоновом воркере; UI с прогрессом/логами не зависает.
- **Кэш:** результат каждой стадии — по хэшу (вход + параметры + версия модели). Повтор не пересчитывает неизменённое. Генеративные проходы (дорогие) кэшируются обязательно.

### 4.5 Каноническая модель сцены
Независимое от моделей и Blender, сериализуемое представление (USD-совместимое + сайдкар-метаданные): мировой фрейм (метры, ось вверх) + плоскость поля + гомография; субъекты (SMPL-X β/θ/root, трек-id, команда); мяч (3D-траектория + достоверность высоты); слои `proposal/corrections/resolved`; покадровая уверенность; ссылки на рендер-ассеты (аватары, сплаты) и на **синтезированные ракурсы** (выход ViewSynthesizer с их камерами).

### 4.6 Архитектурный стиль
**Ports & Adapters (гексагональная архитектура).** Чистое Python-ядро (модель сцены, движок коррекций, контракты оркестрации) **не зависит** ни от Blender, ни от конкретных ML/рендер-бэкендов. Blender и каждая модель (включая ViewSynthesizer) — за адаптерами.

### 4.7 Генеративный novel-view (video-diffusion): два шва интеграции
Инструмент `ViewSynthesizer` подключается **в двух местах** пайплайна:
- **Шов A — рендер-адаптер.** Реализует `RenderPass` для **ограниченных** движений камеры (облёт/доезд вокруг вещательного вида): берёт исходное видео (+ при наличии целевую траекторию/облако точек сцены) и выдаёт фотореалистичное видео с нового ракурса. Быстрый путь до фотореала для умеренных движений, **без редактируемости** (видео, не геометрия).
- **Шов B — амплификатор данных (pre-reconstruction).** Из одной камеры синтезирует доп. ракурсы, которые подаются в `EnvReconstructor`/`AvatarBuilder`, превращая моно в **псевдо-мульти-вью** и повышая качество реконструкции (паттерн «single → синтетический мультивью → 3D»). Также используется для **инпейнта невидимых сторон** игроков.
- **Граница ответственности:** ViewSynthesizer **не** заменяет явную 3D-реконструкцию там, где нужны редактирование (поз/траекторий) или произвольная свободная камера; это **дополнение**, а не замена (см. риски R-14…R-16).

## 5. Функциональные требования

### 5.1 Источник и эпизод
- **FR-1.** Проект: создание/сохранение/открытие; хранит источник, эпизоды, слои правок, ассеты, синтезированные ракурсы, настройки.
- **FR-2.** Импорт источника: видео и последовательности кадров; метаданные (fps, разрешение, таймкод).
- **FR-3.** Выбор эпизода: ручные временные диапазоны на таймлайне.
- **FR-4.** Авто-детекция моментов (action spotting) + детекция границ планов/повторов; отсечение непригодных участков.

### 5.2 3D-реконструкция (ядро, моно)
- **FR-5.** Детекция: игроки/вратари/судьи/мяч (per-frame).
- **FR-6.** Трекинг с устойчивыми ID; классификация команд.
- **FR-7.** Гомография поля; проекция точек опоры (ступни) → мировые (x, y). **Мировой якорь.**
- **FR-8.** HMR → SMPL-X (θ, β) по кадрам. **Root из гомографии**; контакт стоп с плоскостью (anti-foot-sliding).
- **FR-9.** Трекинг мяча + подъём в 3D: 2D-трек → 3D; высота — баллистикой; явная достоверность высоты.
- **FR-10.** Идентификация (опц.): OCR номеров + re-id.

### 5.3 Фотореалистичный слой (обязателен; стадийно)
- **FR-11. Окружение.** 3D Gaussian Splatting / NeRF по движению камеры; генеративный стадион как фолбэк. Рендер сплатами.
- **FR-12. Игроки — фотореалистичные аватары.** Три комбинируемые стратегии: (1) текстурированный SMPL-X (база MVP); (2) генеративный аватар (Rodin-класс) из референс-кропа → ригг → привод SMPL-анимацией; (3) per-subject анимируемый Gaussian-аватар (3DGS-Avatar/GaussianAvatar/Animatable Gaussians/ASH-класс).
- **FR-13. Мяч.** Текстурированная сфера на 3D-траектории.
- **FR-14. Рендер-пасс.** Сборка фотореалистичного кадра/последовательности из текущего состояния сцены через 3DGS/avatar-рендерер. Состояние — из SMPL/кривых.

### 5.4 Редактор и коррекция (на прокси-представлении)
- **FR-15.** Просмотр: свободная камера (орбита/облёт), камера «от лица игрока» (head-joint), пресеты.
- **FR-16. Оверлей репроекции:** рендер 3D обратно на исходный кадр.
- **FR-17. Карта уверенности:** подсветка проблемных кадров/суставов/субъектов.
- **FR-18.** Редактирование поз: кости/части тела гизмо; правка формы (β).
- **FR-19.** Редактирование траекторий: мяч и корневые трансформации как **F-curves**; ключи, интерполяция, сглаживание.
- **FR-20.** Редактирование расстановки на виде «сверху» (2D-радар), синхронно с 3D.
- **FR-21.** Недеструктивность: правки — **дельты поверх предложения**; сравнение/сброс/переключение слоёв.

### 5.5 Перенос правок на другие кадры (критическая фича)
- **FR-22.** Режимы распространения на выбранный диапазон/набор кадров: **(a)** constant offset; **(b)** интерполяция между ключами; **(c)** re-fit по подсказке (constraint-guided HMR на выбранных кадрах); **(d)** temporal smoothing.
- **FR-23.** Предпросмотр результата до применения; применение атомарно и обратимо (undo).
- **FR-24.** Пакетная коррекция: одна операция на несколько субъектов/диапазонов.

### 5.6 Версионирование и экспорт
- **FR-25.** История правок; именованные снапшоты; откат.
- **FR-26.** Экспорт сцены: glTF/GLB, USD, FBX, Alembic; SMPL-X анимация (.npz) отдельно.
- **FR-27.** Экспорт веб-просмотрщика (three.js / R3F): сцена + покадровое состояние.
- **FR-28.** Экспорт промежуточных данных (трек/гомография/поза/траектория мяча в JSON); экспорт синтезированных видео-ракурсов (выход ViewSynthesizer) как видео-файлов.

### 5.7 Инструмент: генеративный novel-view (video-diffusion) — ViewSynthesizer
- **FR-29. Режим «рендер-адаптер» (шов A).** Сгенерировать фотореалистичное видео эпизода с **новой ограниченной траектории камеры** вокруг вещательного вида, на основе исходного видео (и, при наличии, целевой траектории/3D-подсказок сцены). Используется как альтернативный, нередактируемый рендер-выход для умеренных движений/кинематографичных облётов.
- **FR-30. Режим «амплификатор» (шов B).** Сгенерировать N дополнительных синтетических ракурсов из одной камеры и передать их в реконструкцию (`EnvReconstructor`/`AvatarBuilder`) как псевдо-мульти-вью; число ракурсов и диапазон отклонения камеры — параметры.
- **FR-31. Режим «инпейнт окклюзий».** Сгенерировать правдоподобный вид невидимых сторон субъектов для дополнения аватар-пайплайна (стратегии #2/#3).
- **FR-32.** Все режимы — офлайн-задачи в очереди с обязательным кэшированием результата (дорогие генеративные проходы); прозрачность модели/версии/стоимости (UX-7). Выбор конкретной модели — на уровне адаптера (см. стек).

### 5.8 Расширения вне MVP (точки роста, не реализуются сейчас)
- Мульти-вью реальных камер: несколько синхронных откалиброванных источников, триангуляция/мультивью-фиттинг SMPL-X, мяч триангуляцией. Архитектурно предусмотреть шов (камеры — список, гомография как частный случай калибровки), но **не строить** в MVP. (Примечание: ViewSynthesizer-«амплификатор» использует тот же мультивью-вход — синтетическими ракурсами.)

## 6. Требования к UI/UX и эргономике

- **UX-1. Раскладка «студия → редактор».**
- **UX-2. Связанный таймлайн** (кадр-источник + 3D + оверлей репроекции; маркеры моментов/планов).
- **UX-3. Тумблер представлений:** прокси ↔ фотореал, proposal ↔ resolved; сплит «оригинал/правка». Для рендера — выбор пути: **3DGS/аватары (свободная камера)** или **ViewSynthesizer (ограниченный облёт)**.

- **UX-5. Недеструктивность по умолчанию** («Reset to model» на каждом уровне).
- **UX-6. Kbd-first доводка.**
- **UX-7. Прозрачность пайплайна** (модель/версия/параметры/уверенность/стоимость API; для ViewSynthesizer — явная пометка «видео, не редактируется»).
- **UX-8. Прогресс и устойчивость** (фоновый воркер; продолжение после сбоя).
- **UX-9. Превью рендер-пасса** (быстрый низкокачественный предпросмотр перед финалом — и для 3DGS/аватаров, и для ViewSynthesizer).
- **UX-10. Единый масштаб/координаты** (метры, ось вверх, привязка к полю).

## 7. Нефункциональные требования

- **NFR-1. Офлайн.** Метрика — качество и предсказуемость, не FPS обработки.
- **NFR-2. Интерактивность редактора.** Плавность на прокси (≤30 с, до ~24 субъектов), UI ≥ 30 FPS. Фотореал/генеративные проходы — офлайн.
- **NFR-3. Железо.** Локальные HMR/детекция/аватары/локальные video-diffusion — GPU (NVIDIA/CUDA); документировать VRAM. Облачные API — без локального GPU.
- **NFR-4. Кэш/идемпотентность.** Особенно для дорогих генеративных проходов (аватары, ViewSynthesizer).
- **NFR-5. Форматы.** Вход: видео/изображения (FFmpeg/GStreamer). Выход: glTF/GLB/USD/FBX/Alembic/JSON; сплаты — совместимый формат для веб-вьюера; синтез-ракурсы — видео.
- **NFR-6. Расширяемость.** Новая модель (включая новый ViewSynthesizer-бэкенд) = новый адаптер без изменения ядра.
- **NFR-7. Воспроизводимость.** Лог параметров и версий моделей на сцену.
- **NFR-8. Лицензии/стоимость.** Внутреннее/исследовательское использование снимает ограничения GPL/AGPL/SMPL; контролировать стоимость генеративных API (особенно ViewSynthesizer).

## 8. Подводные камни и риски

- **R-1…R-13.** (См. v0.2: фотореал из одной точки = синтез не копия; стоимость per-subject аватаров; синхронизация edit↔render; высота мяча; окклюзии/ID; дрейф гомографии; foot-sliding; 3DGS требует движения камеры; интеграция рендера сплатов; неблокирующий UI; качество авто-этапа; доменный сдвиг; права на контент.)
- **R-14. ViewSynthesizer: ограничение перекрытия фрустумов.** Генеративный novel-view требует достаточного overlap с исходным видом → это **ограниченный перенацел камеры**, а не произвольный free-viewpoint. Сильное отклонение (вид со спины, top-down из боковой трансляции) уходит в галлюцинацию. → Шов A — только умеренные движения; произвольная камера — через явную 3D.
- **R-15. Выход ViewSynthesizer — пиксели, не геометрия.** Редактировать позы/траектории в сгенерированном видео нельзя. → Это «просмотровый/кинематографичный» и «амплификационный» инструмент; путь редактирования остаётся на SMPL/кривых.
- **R-16. Толпа/люди — тяжёлый кейс генеративного novel-view.** Многолюдные быстрые сцены с окклюзиями → мерцание, дрейф идентичности, артефакты на 30-сек клипе; достоверность инпейнта невидимого — правдоподобная, не точная. → Контроль качества (превью, оверлей), ограничение диапазона, выборочное применение; для анализа критичных позиций не полагаться на генеративную «достройку».

## 9. Рекомендуемый стек (моно + фотореал)

> Версии моделей — на момент составления (середина 2026); адаптеры позволяют обновлять без изменения ядра.

**Платформа/UI/редактор:** Blender (`bpy`) + Meshcapade SMPL-X аддон; опц. оболочка PySide6. Видео-I/O — FFmpeg/GStreamer; сервис моделей — PyTorch (+ ONNX/TensorRT); фоновый воркер + контентно-адресуемый кэш.

**Детекция/трекинг/команды:** RF-DETR (основной); YOLO26/YOLOv12 (быстрые); старт на `roboflow/sports`. Трекинг — ByteTrack/BoT-SORT + re-id.

**Калибровка поля:** keypoint-модель разметки (Roboflow `football-field-detection`) → `findHomography`/`ViewTransformer` + temporal-сглаживание.

**Поза/тело:** GVHMR (gravity-view, SMPL-X) / WHAM / TRAM; HumanMM (склейки); PromptHMR (constraint-guided re-fit).

**Мяч:** TrackNet-семейство (2D) + баллистика.

**Эпизоды:** SoccerNet Action/Team-Ball Spotting (бейзлайн T-DEED), детекция границ планов.

**Окружение (фотореал):** 3D Gaussian Splatting / NeRF (gsplat) по движению камеры; генеративный стадион — фолбэк.

**Аватары (фотореал):** генеративные API (Rodin-класс; Meshy/Tripo/TRELLIS-2 — ассеты/текстуры) + per-subject Gaussian-аватары (3DGS-Avatar/GaussianAvatar/Animatable Gaussians/ASH-класс).

**Генеративный novel-view (ViewSynthesizer):** ReCamMaster, TrajectoryCrafter, GCD (Generative Camera Dolly), GEN3C, ViewCrafter; для мульти-камерной синхронизации — SynCamMaster. Подключаются как адаптеры за портом `ViewSynthesizer` (швы A и B).

**Идентификация (опц.):** OCR номеров (PARSeq-класса) + re-id; ориентир — SoccerNet Game State Reconstruction.

**Экспорт/веб:** glTF/USD/FBX/Alembic; веб-просмотр — three.js / React Three Fiber.

## 10. Этапность (моно сквозь все этапы)

1. **M0 — Каркас.** Проект, источник, таймлайн, каноническая модель сцены, очередь + кэш, гексагональное ядро, экспорт glTF.
2. **M1 — Замкнутый редактируемый цикл.** Детекция+трекинг+гомография+HMR, расстановка, мяч (по земле), **прокси**, оверлей репроекции, редактирование поз/траекторий, перенос правок. Артефакт: 3D-сцену на клипе можно **отредактировать**.
3. **M2 — Фотореалистичный слой.** 3DGS/NeRF-окружение; генеративные аватары (#2) + текстур-SMPL (#1); рендер-пасс; синхронизация edit↔render. **Здесь же — ViewSynthesizer шов A** (альтернативный рендер для ограниченных облётов) как опциональный путь. Артефакт: фотореалистичный рендер отредактированной сцены.
4. **M3 — Качество и доводка.** Per-subject Gaussian-аватары (#3) выборочно; constraint-guided re-fit; **ViewSynthesizer шов B** (амплификация мультивью + инпейнт окклюзий) для подъёма качества реконструкции; карта уверенности/приоритезация; версии/откат; веб-экспорт.
5. **M4 (опц.) — Мульти-вью реальных камер** (см. 5.8).

На каждом шаге — работающий сквозной артефакт на реальном клипе.

## 11. Критерии приёмки (примеры)

- **AC-1.** Из одного видео-эпизода — 3D-сцена с расставленными анимированными игроками и мячом; оверлей репроекции совпадает с исходником на широких планах.
- **AC-2.** Оператор исправляет позу игрока и **переносит** правку на диапазон тремя способами (offset/interp/re-fit) с предпросмотром и откатом.
- **AC-3.** Траектории мяча и игроков редактируются как кривые; изменения отражаются в 3D, рендер-пассе и экспорте.
- **AC-4.** Рендер-пасс выдаёт фотореалистичный кадр; правка SMPL-позы корректно перепроецируется в фотореал без ручной переделки.
- **AC-5.** ViewSynthesizer шов A выдаёт фотореалистичный облёт ограниченного диапазона из исходного видео; результат кэшируется. Шов B выдаёт N синтетических ракурсов, принимаемых реконструкцией как мультивью-вход.
- **AC-6.** Экспорт (glTF/USD/FBX) и веб-просмотрщик (three.js) открываются во внешних инструментах без потери масштаба/координат.
- **AC-7.** Ядро (модель сцены + математика коррекций + оркестрация) проходит автотесты с фейковыми адаптерами (включая `FakeViewSynthesizer`) **без GPU и без Blender**.
