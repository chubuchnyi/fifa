Версия от 2026-07-29. Назначение: тренерская аналитика матчей и тренировок.

## 1. Что определяет архитектуру

Задача распадается на четыре подзадачи с радикально разными характеристиками ошибки. Смешивать их в «пайплайн 3D-реконструкции» — источник плохих решений.

| Подзадача | Достижимо сегодня | Статус |
|---|---|---|
| Поза камеры (world ↔ image) | ~0.04°/кадр по повороту, дрейф накапливается | **Доминирующий источник ошибки** |
| Планарная позиция игрока (x, y) | 0.1–0.5 м | Практически решено |
| Артикуляция (local pose) | ~5 см MPJPE | Достаточно для большинства задач |
| 3D мяча, особенно высота | Не измеряется вне баллистики | **Самое слабое звено** |
| Позиции невидимых игроков | 10–17 м медианы | Оценка, не измерение |

### Реперные точки

- **FIFA Skeletal Tracking Challenge 2026** (одна broadcast-камера, ЧМ-2022, 50 fps, 1080p). Победитель SMART (arXiv 2605.31551): Global MPJPE **0.324 м**, Local MPJPE **0.054 м** `[изм.]`. Бейзлайн FIFA на SAM-3D-Body — 1.053 по композиту `Score = Global + 5×Local`, победитель 0.593.
- Глобальная ошибка даёт **~55%** итогового скора `[изм.]`. Камера, а не лифтер.
- Мультикамерный индустриальный референс (Tracab, LaLiga): **~10 см** при 25 fps `[изм.]`. Мы втрое хуже — проговаривать клиенту до контракта.
- Broadcast показывает **10–16 из 22** игроков (arXiv 2607.11548); FOOTPASS сообщает 9–12; Graph Imputer — 12.8 ± 3.7 `[изм.]`.
- Игнорирование невидимых искажает pitch control в скрытых зонах на **25.1–26.9 п.п.** и долю контроля на **11.1–13.4 п.п.** `[изм.]`.
- Метрика GS-HOTA **оценивает только видимых игроков** — стандартный протокол GSR структурно не видит эту проблему.

## 2. Архитектурный принцип

**Один оконный MAP-оптимизатор на шот, а не каскад.**

Feed-forward конвейер, где каждый блок отдаёт точечную оценку следующему, — неверная топология. Ошибка калибровки распространяется вниз необратимо: к моменту оценки поз изображение уже выброшено, и восстановить нечем.

Второе следствие того же принципа: **физика соревнуется с данными в одном функционале**. Констрейнт, запущенный отдельным пост-этапом, не видит пикселей и разрешает коллизии произвольным сдвигом людей, уничтожая наблюдения. Все физические ограничения — мягкие residuals с весами, ни один не имеет права затирать репроекцию.

Третье: **правдоподобие ≠ точность**. Физический слой оптимизирует правдоподобие (нулевые residual forces, GRF около веса тела). На входе 15–40 пикселей на игрока это измеряет вашу модель, а не игрока. Аналитическая истина всегда берётся с кинематического слоя.

## 3. Стадии

### 3.1. Шоты и типы кадров

Классификатор: main camera / повтор / крупный план / студия.

- Main camera → пайплайн поз
- **Крупные планы → только оценка `β`** (см. §4.5). Это единственное применение отброшенного материала, и оно ценное
- Повторы и студия → выброс

Склейки не сшиваются: каждый шот — независимая задача оптимизации. Отсутствие этого блока — причина, по которой пайплайн ломается на первом реальном матче.

### 3.2. Детекция, трекинг, идентификация

- **Детектор:** RF-DETR или YOLO26, дообученный на SoccerNet. Оба использованы победителями SoccerNet 2026.
- **Мелкие объекты:** адаптивный тайлинг (Boundary-Aware Adaptive Tiling у победителя SynLoc-2026) или SAHI с NMS-мержем через границы тайлов.
- **Трекинг:** BoT-SORT / ByteTrack + ReID.
- **Идентификация:** OCR номеров + кластеризация цвета торса. Для тренировок с манишками — переобучение кластеризатора, не open-vocab детекция (см. §9).
- **Ремонт треклетов:** FSM `search → candidate → repair`, слияние по геометрии + внешности + кинематике.
- **Ориентир по фрагментации:** в реальном GSR-пайплайне покрытие OCR номеров ~45% `[изм.]`, и ~20% событий вообще не имеют bbox. Планировать под это, а не под идеальный трекинг.

Готовый каркас: **TrackLab / sn-gamestate**.

### 3.3. Калибровка — критический путь

**Per-frame регистрация к модели поля.** PnLCalib (Gutiérrez-Pérez & Agudo, CVIU 267, 104712, апрель 2026; arXiv 2404.08401) или No Bells Just Whistles. Инициализация и восстановление после сбоев.

**Темпоральное распространение камеры.** Плотный поток, не разреженный:
- RAFT-small, поток внутри выпуклой оболочки проекций разметки, шаг 4
- MAD-отсев 3σ для векторов, загрязнённых движением игроков
- RANSAC-гомография (2000 итераций, порог 1 px), отбрасывание обновлений с \|ΔR\| > 60°
- Ошибка поворота **0.041°** против 0.043° у Lucas–Kanade `[изм.]`. RAFT-large — 0.041° при двойной стоимости, не нужен. ECC-гомография деградирует (0.107°): игроки занимают слишком много кадра

**Windowed bundle adjustment** на шот: поле как фиксированная 3D-структура, `K_t` как параметр.

**Края линий вместо центральных.** IFAB регламентирует ширину линии (≤12 см). Значит два края каждой линии — это две параллельные прямые на известном разносе вместо одной центральной: бесплатный дополнительный констрейнт, лучше обусловленный на крупных планах. Выпадает из того же фиттинга, без измерения «толщины» как отдельной величины.

**Инструментарий OpenCV 5.** USAC — дефолтный бэкенд всех робастных оценок (гомография, E/F, PnP) с MAGSAC++, LO-RANSAC, GC-RANSAC, PROSAC, ранним завершением через SPRT. На загрязнённом игроками поле это даёт больше, чем смена детектора фич. `calib3d` разбит на `geometry` / `calib` / `stereo` / `ptcloud`. Внимание: **новый DNN-движок работает только на CPU**, GPU в следующих релизах; для NVIDIA — либо классический движок, либо сборка с ONNX Runtime и NVIDIA EP.

**Watchdog:** TCE (Temporal Consistency Error) как онлайн-детектор скачков гомографии.

### 3.4. Лифтер поз

**SMPLest-X (ViT-H, 687M), дообученный на WorldPose.** Дообучение не опционально: off-the-shelf даёт композит 0.846, полный рецепт — 0.647 `[изм.]`.

Абляция, порядок вклада:

| Шаг | Global | Local | Score |
|---|---|---|---|
| Бейзлайн FIFA (SAM-3D-Body) | 0.602 | 0.090 | 1.053 |
| SMPLest-X pretrained | 0.522 | 0.065 | 0.846 |
| + наивный fine-tune | 0.425 | **0.079** ↑ | 0.820 |
| + foot-plane anchoring | 0.381 | 0.067 | 0.714 |
| + stratified split, depth, аугментация | 0.370 | 0.055 | **0.647** |

Три вещи дают основной выигрыш:

1. **Супервизия глубины таза** в камерном пространстве — доминирующий фактор. Без неё local застревает на 0.067 м независимо от аугментаций.
2. **Foot-plane anchoring** — луч через нижний пиксель стопы × плоскость поля: **−44 мм** global, **−12 мм** local.
3. **Stratified split по границам клипов.** Наивный хронологический сплит улучшает global, но **ухудшает** local с 0.065 до 0.079: соседние клипы делят ракурс, модель переобучается на него.

Рецепт: бэкбон заморожен, тренируются декодер и головы; 15 эпох, batch 16, Adam, LR 2e-6, AMP, 1×A10G 24 ГБ. Веса лоссов 1.0 / 0.1 / 0.5 (3D / 2D / depth), по-суставные веса 3.0 для запястий, лодыжек, больших пальцев. Broadcast-аугментация: random resized crop (0.75–1.0, p=0.8), горизонтальный флип с перестановкой симметричных суставов, colour jitter ±0.4 / ±0.1 hue.

**Не подключать VO/SLAM.** GVHMR, TRAM, WHAM решают world-grounding одометрией — у вас метрическая модель поля уже есть, VO избыточен и вносит дрейф. Брать темпоральную часть, не глобальную привязку.

### 3.5. Темпоральный слой — под гейтом

Обученный рефайнер (27 кадров, hidden 128) снизил local на 22% на своей валидации, но **ухудшил** соревновательный результат: 0.680 против 0.647 `[изм.]`. Причина — переглаживание быстрых действий, слабо представленных в обучающем распределении.

Это проблема распределения, не архитектуры. Масштаб подсказывает: 27 кадров при 50 fps = 540 мс, фаза замаха при ударе — 150–250 мс. Окно вдвое-втрое длиннее события, безусловная модель регрессирует к среднему по окну.

Проверяемые ходы: окно 9–13 кадров; ресемплинг по перцентилю скорости суставов; асимметричный лосс, штрафующий недооценку пика; гейт, обусловленный величиной движения, чтобы модель училась ничего не делать на быстрых фазах.

**Гейт для включения в критический путь:** рефайнер обыгрывает гауссово сглаживание на held-out, **стратифицированном по скорости суставов, в верхней децили**. Обычная валидация этот провал не видит — усредняет по кадрам, где большинство медленные.

До прохождения гейта — двухпроходное гауссово сглаживание:
- глобально: MAD ×5 → линейная интерполяция → гаусс σ=3 кадра, кламп 0.35 м/кадр
- локально по суставам: независимый гаусс σ=1.5 кадра при **замороженном** мировом центроиде (иначе проходы мешают друг другу)

### 3.6. Off-screen импутация — P0

Обязательна, если считаются командные метрики.

Лестница методов (arXiv 2607.11548, Metrica, 3 матча, третий held-out, W=44 м):

| Метод | hidden ctrl MAE (п.п.) | share err. (п.п.) | median pos. err. (м) |
|---|---|---|---|
| B0 игнор | 26.9 / 25.6 / 25.1 | 13.4 / 12.5 / 11.1 | — |
| B1 last-seen с затуханием | 22.1 / 20.0 / 19.5 | 10.6 / 9.5 / 8.2 | 19.6 / 17.9 / 18.4 |
| **B2 formation anchor** | 15.7 / 14.6 / 14.3 | 6.2 / 5.4 / 4.4 | 13.6 / 12.8 / 12.5 |
| B3 EMA + скорость | 12.8 / 11.8 / 13.2 | 5.7 / 4.6 / 4.7 | 14.6 / 14.0 / 15.1 |
| **B4 centroid voting** | 13.3 / 12.2 / 13.8 | **4.7 / 4.5 / 4.7** | **11.6 / 10.0 / 9.7** |
| B5 фиксированный шаблон | 23.0 / 18.8 / 19.1 | 10.3 / 7.7 / 6.9 | 22.7 / 20.7 / 21.9 |

Выводы для внедрения:

- **B2 даёт 60% выигрыша тривиально**: «команда сдвинулась, игрок сохранил роль». Это первый шаг, он почти бесплатный.
- B4 добавляет снятие смещения от кадрирования: каждый видимый игрок голосует за центроид всей команды, вычитая свой ролевой офсет. Лучший по позиционной ошибке во всех трёх матчах.
- **B5 — чистый отрицательный результат**: фиксированный шаблон формации хуже любого динамического якоря. Роли дрейфуют внутри тайма.
- Всё это **каузально, без обучения, быстрее реального времени на одном ядре CPU** `[изм.]`. Стоимость включения близка к нулю.
- Гиперпараметры: τ=8 с для затухания, EMA 0.1, порог трёх голосующих, 1.5 с константа смешивания. Круглые числа, не оптимизировались поиском.

**Ограничение, которое надо знать:** при разрыве >9.6 с медианная ошибка 15.6–16.9 м, и таких наблюдений **50–57%** `[изм.]`. Импутация чинит командные метрики, а не индивидуальные траектории. Обученные модели (Graph Imputer, MIDAS, TranSPORTmer) лучше, когда есть данные для обучения и будущий контекст, но Graph Imputer двунаправленный и сегментирует на окна 9.6 с — то есть не покрывает половину случаев и не работает онлайн.

**Обязательно:** импутированные игроки помечаются флагом и рендерятся отлично от измеренных. Иначе тренер разбирает достроенную сцену как наблюдаемую. Практика из реализации: «призраки» с временем жизни 20 с, добор команды максимум до одиннадцати, снятие призрака при появлении трека в 3 м от предсказания.

**Практический аргумент за P0:** на реальных broadcast-окнах ЧМ импутация сдвинула Space-Creation Index на 15.6 и 17.2 пункта, в одном случае перевернув класс вердикта `[изм.]`. Без неё пространственные вердикты зависят от того, куда смотрела камера.

### 3.7. Мяч — самое слабое звено

**Детекция.** Heatmap по стеку кадров (TrackNet-семейство, TrackNetV6, ICMR 2026) или occlusion-aware темпоральный трекер (TOTNet, CVIU 264, февраль 2026). **Оговорка: обе архитектуры валидированы на ракеточных видах и настольном теннисе, не на футболе.** Переносимость не установлена; дообучение на SoccerNet + собственной разметке обязательно до включения в критический путь. Отдельно обрабатывать «белый мяч на белой линии».

**Три источника 3D-сигнала, фьюзить в общий граф:**

1. **Диаметр в пикселях → метрическая глубина** при известном реальном диаметре. Работает везде, где мяч виден хотя бы частично. Это же — бейзлайн SoccerNet-v3D. Ломается в момент удара: мяч деформируется, перестаёт быть сферой — признак пропадает ровно тогда, когда нужнее всего.
2. **Баллистика с сопротивлением и эффектом Магнуса** между контактами.
3. **События касания** (FOOTPASS / TAAD+DST, с привязкой к игроку) — мяч обязан быть у стопы или головы в момент контакта. Сильнейший констрейнт на высоту.

**Отскок — не упругий.** Коэффициент восстановления газона ~0.6–0.8, зависит от влажности; есть связь спина со скоростью при отскоке. Критично не смещение амплитуды, а смещение **времён переключения** кусочно-баллистической модели: от них зависит весь сегмент. Калибровать restitution по эпизодам с наблюдаемым отскоком, разделять сухой/мокрый газон.

**Валидация — с поправкой к v1.** SoccerNet-v3D (CVPRW 2025, arXiv 2504.10106, github.com/mguti97/SoccerNet-v3D) — это **4051 изображение** с 3D-позицией мяча из триангуляции синхронизированных повторов. ISSIA-3D — двухминутная последовательность с шести камер на 25 fps. Оба валидируют **однокадровую** локализацию, не траекторную реконструкцию. Публичного траекторного GT в футболе нет; для траекторий размечать своё.

**В MVP: `z ≡ 0`.** Воздушные сегменты помечать как неизмеренные. Не оценивать высоту, пока нет либо аудио-TDOA (§5.1), либо собственной разметки.

### 3.8. Airborne-фаза

Foot-plane anchoring ломается, когда игрок в воздухе, а в WorldPose прыжки и падения недопредставлены `[изм.]`. Нужно явное переключение.

**Констрейнт идёт на CoM, не на `root`.** Таз смещён относительно центра масс на ~10–15 см по вертикали, и смещение меняется при сгибании туловища. Парабола, приложенная к `root`, даст артефакт «висящего таза» на ударах головой.

CoM выводится присвоением сегментных масс (de Leva / Dempster) частям меша; `β` уже даёт персональные сегментные объёмы, так что масштабирование индивидуальное, а не табличное. **Валидация:** AddBiomechanics (273 субъекта, >70 ч движения с force plate, >24 млн кадров, открытый) — правильный источник для калибровки оценки CoM из SMPL. Публикации «SMPL CoM против force plate» я не нашёл; это открытый пункт.

**Второй констрейнт, сильнее первого: сохранение углового момента.** В свободном полёте сохраняется не только траектория CoM, но и полный угловой момент относительно CoM. Это независимое соотношение, связывающее всю конфигурацию тела между кадрами. Прыжок с подгибом ног — показательный случай: CoM летит по параболе независимо от конфигурации, подгибание меняет момент инерции, и при постоянном угловом моменте угловая скорость обязана вырасти. Проверяемо, и ловит ошибки лифтера, которые парабола CoM пропускает.

**Классификатор контакта — не отдельная сеть, а residual.** Признаки: высота лодыжки над плоскостью поля, вертикальная скорость стопы, площадь контакта из маски. Мягкая бинарная переменная с гистерезисом, оптимизируемая совместно. Жёсткое переключение даст дребезг на границе.

### 3.9. Физический слой — второй проход, опционально

| Инструмент | Дифференцируемость | Статус 2026 |
|---|---|---|
| **MJX** (MuJoCo + JAX) | **Да**, автоматически | Рабочий выбор для дифференцируемой физики |
| MuJoCo Warp | **Нет** (открытый issue) | Быстрее MJX на NVIDIA |
| Isaac Lab (через Newton) | Нет | Актуальная замена Isaac Gym |
| Isaac Gym | Нет | **Deprecated**, не использовать |
| Unity / Unreal Chaos | Нет | Игровые солверы, не под эту задачу |

Контроллеры: PHC+, MaskedMimic, PhysHMR. **Ragdoll не подходит** — пассивная цепь не бежит, не прыгает и не бьёт по мячу; нужен актуированный контроллер.

**Разделение ответственности:** физический слой — это (а) **метрика качества** (насколько кинематика динамически недопустима) и (б) **презентационный рендер**. Не источник данных.

То же относится к IK-фиксации стопы: она визуально чинит скольжение, но меняет длину шага и тайминг контакта — то, что смотрят в спринтерской механике. Слой обязан быть помеченным и обратимым.

### 3.10. Выходной слой

**Данные (parquet/JSON по кадрам):**
`player_id, team, role, root_xyz, com_xyz, joints_3d, velocity, contact_flags, source ∈ {measured, imputed}, confidence`
Мяч отдельно: `xyz, mode ∈ {on_ground, ballistic, unmeasured}, confidence`

**Аналитика — это и есть продукт:**
- Позиционные: дистанция, скорости, спринты, ускорения
- Пространственные: pitch control (Вороной + скорости + время контроля мяча, модель Spearman), зоны контроля, компактность блока
- **Ориентация корпуса** — измерима из позы и заметно улучшает модели осуществимости паса и EPV (Arbués-Sangüesa et al.). Это то, что даёт 3D сверх обычного трекинга
- Технические: углы тела в момент удара, механика бега

**Визуализация:** лёгкий web-вьювер (three.js). UE 5.8 только под фотореализм; NVS в футболе пока хуже всего работает с наземного ракурса — 59% оценочных видов при менее 2% обучающих камер, лучший PSNR 29.89 `[изм.]`.

## 4. Фактор-граф: спецификация

Опубликованной системы, делающей ровно это на футболе, нет. Ниже — вывод из структуры задачи и аналогов из BA/SLAM. Времена — `[оц.]`.

### 4.1. Переменные

| Переменная | Разм. | Кол-во | Инициализация | Границы |
|---|---|---|---|---|
| `R_t` камера | 3 (so3) | N | RAFT-цепочка от PnLCalib-якоря | \|ΔR\| < 60°/кадр |
| `t_t` камера | 3 | N | То же | высота 5–50 м |
| `f_t` фокус | 1 | N | PnLCalib покадрово, сглажено | монотонность внутри зум-сегмента |
| `k1,k2` | 2 | 1 на шот | PnLCalib | — |
| `β_p` форма | 10 | P **на матч** | медиана SMPLest-X по крупным планам | ±3σ PCA, репараметризация tanh |
| `z_p,t` VPoser latent | 32 | N×P | энкод θ из SMPLest-X | штраф на ‖z‖ |
| `root_p,t` | 3 | N×P | foot-plane anchoring | \|v\|<11 м/с, \|a\|<9 м/с² (мягко) |
| `orient_p,t` | 3 | N×P | SMPLest-X | — |
| `ball_t` | 3 | N | z=0 проекция + диаметр | поле + запас |
| `ω_seg` спин | 3 | сегментов | 0 | ‖ω‖ < 10 об/с |
| `t_switch` | 1 | сегментов | из action spotting | ±0.1 с от события |

Шот 10 с при 25 fps (N=250), 14 видимых игроков: камера 1752, игроки ~133k, мяч ~830. Итого **~136k переменных**.

Границы — **мягкие односторонние hinge**, не жёсткие: жёсткие портят LM. Исключение — `β`, там репараметризация.

### 4.2. Residuals

| Residual | Тип | Вес |
|---|---|---|
| Репроекция 2D-кейпоинтов | Основной член данных | 1.0 |
| Репроекция силуэта (SAM-маска) | Только на спорных кадрах | 0.3 |
| Контакт стопы с полем (`z=0`) | Мягкий, с гистерезисом | 0.5 |
| CoM по параболе при `contact=false` | §3.8 | 0.5 |
| Сохранение углового момента в полёте | §3.8 | 0.2 |
| Непроницаемость (капсульные коллизии) | Active set | 0.3 |
| **Лимиты суставов** | См. ниже | 0.2 |
| Постоянство длин костей | Из `β`, автоматически | — |
| Потолки скорости и ускорения корня | Мягкие | 0.1 |
| Приор на ускорения (гладкость) | Не на позиции | 0.1 |
| Баллистика мяча между контактами | С drag и Магнусом | 0.5 |
| Мяч у стопы/головы в момент касания | Из action spotting | 1.0 |

**Лимиты суставов не бесплатны.** Пространство поз SMPL — axis-angle по суставам, без жёстких ограничений; гиперэкстензия колена получается свободно. Регрессоры её избегают потому, что её избегает обучающее распределение, а не потому, что модель запрещает. Два слоя: штраф на норму VPoser-латента как мягкий приор + явные односторонние hinge на реверс-флексию колена и локтя и на внеосевые компоненты этих одностепенных суставов.

### 4.3. Структура разреженности

Это **в точности структура bundle adjustment**, где «камеры» — кадры, а «лендмарки» — покадровые состояния игроков:

- Репроекция — единственная связь камера↔игрок, и она покадровая
- Внутри игрока временны́е факторы дают блочно-**трёхдиагональную** цепь
- `β` — общая на матч, даёт «голову стрелы» (как интринсики в BA)

Отсюда решение: **Schur-комплемент по игрокам**. Каждая цепь исключается за O(N) прогонкой; остаётся приведённая система на 1752 камерных переменных — плотная, но крошечная, решается напрямую.

**Коллизии ломают независимость цепей, но они редки.** Пары ближе 1.5 м — порядка 5–15% пар в футболе. Active set с релинеаризацией на внешней итерации; связь локальна во времени и пространстве, маргинализация превращается в чуть более широкую ленту.

### 4.4. Стадийная схема

Монолитный солв на 136k не нужен:

```
A. Только камера
   1752 переменных. Ceres/g2o. Миллисекунды. Заморозить.

B. По игрокам независимо, камера заморожена
   P задач по ~9500 переменных. Embarrassingly parallel, батч на GPU.

C. Совместное уточнение с активным набором коллизий
   Только во временных окнах с близкими парами. Обычно 10–20% шота.

Внешний цикл по матчу:
   Пересчёт β по всем шотам → повтор B/C. 2–3 итерации.
```

~90% выигрыша при ~10% сложности, тестируется по стадиям. Монолитный совместный солв — v2 архитектуры, не v1.

**Окно:** длина шота (broadcast main camera — обычно 3–15 с), с ограничением сверху ~10 с и перекрытием 1 с; перекрывающиеся оценки сливаются pose-graph-подобно.

### 4.5. `β` оценивается на выброшенных кадрах

Форма тела восстанавливается тем лучше, чем крупнее игрок в кадре. Крупные планы и повторы, отброшенные в §3.1, — лучший источник `β`. Схема: крупные планы идут **только** в оценку `β` (привязка по номеру через OCR), main camera — в оценку поз.

Это снимает масштабную неоднозначность бесплатно: `β` даёт рост игрока, рост даёт метрический масштаб.

### 4.6. Солвер

Для Python-команды: **PyTorch + Theseus** (LM с разреженным Cholesky, батчинг на GPU). SMPL FK автодифференцируется бесплатно, модель та же, что в обучении. Альтернатива — JAX + свой LM. GTSAM/Ceres зрелее, но SMPL в C++ не окупается.

**LM, не Dogleg:** Dogleg выигрывает при плохой инициализации, а вы стартуете с 0.37 м global. Адаптивное демпфирование, 15–30 итераций `[оц.]`.

Время: десятки секунд на 10-секундный шот на одном современном GPU `[оц.]` — то есть post-match контур. Бенчмаркить, не верить оценке.

## 5. Два контура

### 5.1. Тренировки (камера ваша) — MVP

Статичная 4K на всё поле, разовая калибровка. Убирает доминирующий источник ошибки целиком. Референс достижимого: победитель SynLoc-2026 — **97.67 mAP-LocSim, 81.91% кадров с идеальным предсказанием** при допуске 0.48 м `[изм.]`.

Скоуп MVP:
- Детекция + трекинг + регрессия таза **и его проекции на землю** (RTMPose-X или ViTPose++ на две точки, как у победителей SynLoc). Не центр bbox — он на уровне торса и систематически уносит игрока от камеры
- Позиционные метрики, pitch control, компактность
- Импутация B2 — почти бесплатно, но на статичной камере на всё поле она почти не нужна
- Мяч по газону, `z ≡ 0`
- Позы опционально, покадровым лифтером с foot-plane anchoring и фиксированной `β`. Без физики

**Аудио-TDOA — P1 именно здесь.** См. §9 о том, почему это не работает на broadcast. В тренировочном сценарии рига ваша: четыре дешёвых синхронных микрофона по углам площадки с аппаратным таймстемпом от той же клок-линии, что камера. Акустическая задержка от удара до микрофона — детерминированная функция позиции мяча (τ = |p_мяч − p_мик| / c), то есть не шум, а **измерение дальности**. TDOA по четырём микрофонам даёт прямую мультилатерацию точки удара в 3D, **включая высоту** — ту самую, которую нечем измерить визуально. Стоимость близка к нулю, закрывает слабейший узел пайплайна.

Открытый пункт: precision/recall детекции удара в шумной обстановке я не нашёл. В тренировочном контуре это менее критично — ложные срабатывания отсеиваются несовпадением с визуальной позицией мяча.

### 5.2. Broadcast — v1

Полный пайплайн §3.1–3.8 плюс фактор-граф §4. Здесь нужна вся тяжесть: детектор склеек, PnLCalib + RAFT + BA, дообученный SMPLest-X, импутация B4.

## 6. Латентность и железо

Тренеру на бровке 3D-меш не нужен. Ему нужны позиционные метрики — а они целиком в 2D-контуре плюс калибровка. **Поэтому RAFT не в live-тракте:** live использует покадровую PnLCalib-гомографию, RAFT + BA — офлайновый тракт точности.

| Контур | Содержание | Задержка | Железо |
|---|---|---|---|
| Live | 2D-детекция, трекинг, покадровая гомография, миниматч, скорости, дистанции, спринты, pitch control, импутация B2/B4 | < 1 с | Edge, ноутбук/мини-ПК |
| Перерыв | 3D-позы на выбранных эпизодах, батчем | минуты | Локальный GPU |
| Post-match | Фактор-граф на весь матч, физическая валидация | часы | Облако |

**Измеренное:**
- RAFT-small камера: 55 мс/кадр; RAFT-large 110 мс без выигрыша по точности
- ViT-S даёт ~4× ускорение против ViT-H `[заявл.]`, абсолютных чисел авторы не приводят

**Оценка `[оц.]`, арифметика показана для проверки:** ViT-H/14 на 512×384 ≈ 1000 токенов, ~1.3 TFLOP на кроп. A10G на реалистичных 40% пика ≈ 50 TFLOPS → ~25 мс на кроп без батча, 10–15 мс с батчем. 14 игроков × 25 fps = 350 кропов/с → ~4–5 GPU-секунд на секунду видео, то есть **~5 A10G на real-time при 25 fps, ~9 при 50**. Отсюда и следует, что 3D — не live-контур. Замерить на своём железе.

### 6.1. ViT-S: supervised, не дистилляция

Возражение «дистиллировать от учителя с 30–40 см ошибки» смешивает два члена. Global 32 см доминируется **камерой** (~55% скора), а не лифтером. Собственная ошибка лифтера — local MPJPE 5.4 см. Для локальной позы учитель хороший.

Но лучше дистилляции: **у вас есть GT**. Обучать ViT-S напрямую на WorldPose тем же рецептом (§3.4). Дистилляция окупается только на неразмеченных данных — своих матчах. Правильная схема полу-supervised: WorldPose как GT + псевдо-метки на своём материале.

**Специализация не на команду** (состав меняется), а **на условия съёмки**: стадион, камера, освещение. Это стабильно и не ломается на трансферах.

## 7. Валидация и бюджет ошибки

| Что | Датасет / метрика | Цель |
|---|---|---|
| Калибровка | Ошибка поворота против GT-поз камеры (WorldPose) | < 0.05°/кадр |
| Планарная локализация | mAP-LocSim (SynLoc) | > 90 на статичной камере |
| Глобальная поза | Global MPJPE (WorldPose / протокол FIFA) | 0.35–0.45 м broadcast; < 0.15 м статичная |
| Артикуляция | Local MPJPE | < 0.06 м |
| Артикуляция, быстрые фазы | Local MPJPE, **верхняяециль по скорости суставов** | не хуже, чем в среднем ×1.5 |
| Мяч, однокадровая | SoccerNet-v3D (4051 изобр.) | По бейзлайну авторов |
| Мяч, траектории | **Собственная разметка** — публичного GT нет | Доля покрытия по режимам |
| Командные метрики | Ошибка pitch control против полного трекинга (Metrica, открытые) | < 10 п.п. |
| CoM | AddBiomechanics (force plate) | Открытый пункт |

**Ловушки метрик, которых избегать в отчётности:**
- **GS-HOTA** — метрика 2D-миниматча, к 3D-позе отношения не имеет и **не учитывает невидимых игроков**
- Лабораторные Vicon-числа (6–8 см) неприменимы к broadcast — расхождение вчетверо
- SoccerNet-Depth — относительная глубина, метрика безразмерная
- Метрики физической правдоподобности (residual forces, GRF) измеряют вашу модель, а не игрока
- Средний MPJPE скрывает провал на быстрых фазах — стратифицировать

## 8. Режимы отказа

| Отказ | Причина | Митигация |
|---|---|---|
| Игрок в воздухе | Foot-plane ломается; прыжки недопредставлены в WorldPose | Детектор airborne, констрейнт на CoM + угловой момент (§3.8) |
| Агрессивный зум | Кажущаяся деформация плоскости ломает гомографию; global до ×2 | `K_t` как параметр, детекция режима зума |
| Затяжная окклюзия | Покадровый лифтер хрупок | Occlusion-aware слой; порядок по дальности из точек контакта |
| Скопление (угловой, стенка) | Стопы не видны ни у кого | Depth Anything V2 (дообученный на SoccerNet-Depth) как приор упорядочивания; SAM-маски |
| Мяч в момент удара | Деформация ломает признак диаметра | Событие касания + баллистика соседних сегментов |
| Половина команды вне кадра | Свойство broadcast | Импутация B4 + обязательный флаг (§3.6) |
| Фрагментация идентичности | OCR номеров ~45% покрытия | Ролевая привязка вместо идентичности; ReID по внешности как следующий шаг |
| Мокрый газон | Меняется restitution → смещаются времена переключения | Раздельная калибровка сухой/мокрый |

## 9. Отклонённое и почему

Чтобы не переоткрывать. Каждый пункт был всерьёз рассмотрен.

| Идея | Вердикт | Причина |
|---|---|---|
| **NeRF/PixelNeRF для калибровки** | Отклонить | У вас есть метрическая CAD-модель сцены (поле 105×68 с регламентированной разметкой). NeRF даёт внешний вид, а не отсутствующую геометрию |
| **ALIKED/LightGlue как основной матчер поля** | Отклонить | Газон однороден и периодичен, поле почти зеркально симметрично (алиасинг половин), треть кадра — движущиеся игроки. Семантическая детекция линий к известной модели выигрывает. (Сами методы в OpenCV 5 есть — в модуле Features) |
| **Тень мяча для высоты** | Отклонить | Азимут и высота солнца считаются из геолокации и таймстемпа бесплатно — блокирует не геометрия, а детекция: эллипс тени 3–4 px. Плюс ночные матчи с многократными мягкими тенями, пасмурная погода, перекрытие в штрафной |
| **Толщина линий как независимый констрейнт** | Отклонить, но переформулировать | Перспектива меняет толщину без всякого зума; нужна дальность до линии — курица и яйцо. Спасаемая версия: два **края** линии как две параллельные прямые на регламентированном разносе (§3.3) |
| **Аудио на broadcast** | Отклонить | Скорость звука даёт 87–290 мс задержки, зависящей от позиции эпизода (2–7 кадров при 25 fps). Это вычислимо, но приходит **сведённый программный звук**, а не многоканальный полевой фид — мультилатерация невозможна. Для тренировок инвертируется в P1 (§5.1) |
| **Игровой движок как пост-фильтр** | Отклонить | Не видит пикселей: разрешает коллизии произвольным сдвигом людей, уничтожая наблюдения. Констрейнты — в тот же функционал (§2) |
| **Ragdoll для SMPL** | Отклонить | Пассивная цепь не бежит, не прыгает, не бьёт. Нужен актуированный контроллер |
| **MPC / iLQR для сглаживания** | Отклонить | Метод управления с приёмным горизонтом, а не оценивания. Офлайн нужен batch MAP. «Минимизировать энергию» смещает ровно ту величину, которую измеряют |
| **Упругий отскок мяча** | Отклонить | Restitution газона 0.6–0.8, зависит от влажности; ошибка смещает времена переключения |
| **YOLO-World / CLIP для смены формы** | Отклонить | Решает задачу, которой нет. Манишки — это задача **назначения команды**, решается кластеризацией цвета торса в пределах матча |
| **G-API в OpenCV 5** | Неприменимо | Модуль перенесён в `opencv_contrib` |
| **Isaac Gym** | Неприменимо | Deprecated, замена — Isaac Lab |
| **UE5-синтетика для внешнего вида** | Отложить (P3) | Domain gap по спектральным артефактам, motion blur, H.264 реален для ReID и OCR |
| **UE5-синтетика для геометрии** | **Принять (P1)** | Доказано в этом домене: SynLoc построен на синтетике, победитель 2026 — 97.67 mAP-LocSim; SoccerNet MDE 2025 использовал синтетику для глубины; NVS-2026 сделан в Blender по реальным трансляциям с IK по реальным 3D-координатам |

### Foundation models — где окупаются

- **SAM 2/3** — не для детекции, а для **силуэтного residual** и упорядочивания по дальности при скоплениях. Дорого (энкодер SAM2 — тяжёлый). Только на выбранных кадрах: угловые, стенка, борьба в штрафной
- **DINOv2** — как бэкбон ReID-эмбеддингов. Там и окупается. Не как бэкбон детектора
- **Depth Anything V2** (дообученный на SoccerNet-Depth) — вспомогательный приор упорядочивания там, где стоп не видно. Не второй уровень пайплайна: для всего, что касается газона, плоскость поля даёт метрику точнее
