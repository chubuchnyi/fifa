**Файл-источник истины:** `TZ_3D_football_reconstruction.md` (v0.3) в этом репозитории. Прочитай его первым. При конфликте: **требования** определяет ТЗ; **форму архитектурного результата** определяет этот бриф.

> Обновление: в тулкит добавлен инструмент генеративного novel-view (video-diffusion) под портом `ViewSynthesizer` с двумя швами интеграции (рендер-адаптер и амплификатор данных) — учти в архитектуре, контрактах, ADR и фейках.

## 0. Роль и режим работы

Ты действуешь как **software architect**, а не как разработчик фич. Цель прогона — превратить ТЗ в **конкретную, обоснованную архитектуру и каркас репозитория**: контракты, типы, структуру пакетов, ADR, диаграммы, план реализации и заглушки. **Тяжёлый ML/CV/рендер/генеративные модели сейчас НЕ реализуем** — только интерфейсы, типы, scaffolding и один сквозной «dry-run» на фейковых адаптерах.

Перед написанием кода: прочитай ТЗ, **перескажи архитектуру своими словами** и выпиши открытые вопросы/допущения. Где неоднозначно — **прими дефолт, зафиксируй в ADR и продолжай**. Не блокируйся на вопросах.

## 1. Краткая выжимка ограничений (чтобы не дрейфовать)

- Язык/платформа: **Python**, десктоп. Платформа редактирования — **Blender** (`bpy`) + Meshcapade SMPL-X аддон (иначе — обоснуй в ADR).
- Объём MVP: **моно** (1 источник, 1 точка обзора). Мульти-вью реальных камер — только архитектурный шов, **не реализовывать**.
- **Двойная репрезентация:** edit = SMPL-X (θ, β, root по кадрам) + кривые (мяч, корневые траектории) на прокси; render = 3DGS/NeRF-окружение + фотореал-аватары + текстур-мяч. **Единый источник истины — SMPL/кривые**; рендер (включая видео-выход ViewSynthesizer) строго производный, **не редактируется напрямую**.
- **Инструмент `ViewSynthesizer` (video-diffusion novel-view).** Подключается в двух швах: **(A) рендер-адаптер** — реализует `RenderPass` для ограниченных движений камеры (облёт вокруг вещательного вида), выход — видео; **(B) амплификатор данных** — синтез доп. ракурсов из одной камеры на вход реконструкции (моно → псевдо-мульти-вью) и инпейнт невидимых сторон. **Caveat:** ограничение перекрытия фрустумов (только умеренные движения), выход — пиксели, не геометрия; это **дополнение**, не замена явной 3D-реконструкции.
- **Стиль: Ports & Adapters (гексагональная архитектура).** Чистое ядро **не импортирует** `bpy` и ни одной ML/рендер-библиотеки.
- Исполнение: офлайн **очередь задач** + **контентно-адресуемый кэш** (хэш входа+параметров+версии модели). Дорогие генеративные проходы (аватары, ViewSynthesizer) кэшируются обязательно. UI не зависает.
- Фотореал обязателен, стадийно: M1 — редактируемый цикл на прокси; M2 — фотореал-слой (+ ViewSynthesizer шов A опц.); M3 — качество (+ ViewSynthesizer шов B).
- Использование: внутреннее, личное/исследовательское (лицензии GPL/AGPL/SMPL допустимы; контролируем стоимость API).

## 2. Объём работ (что произвести)

1. **Уточнить и заострить архитектуру.** Зафиксируй решения отдельными ADR: (a) платформа редактирования; (b) двойная репрезентация и механизм синхронизации edit→render; (c) интеграция рендера сплатов; (d) очередь задач + кэш; (e) формат сериализации сцены (USD vs кастом); (f) формат обмена с веб-вьюером (three.js); **(g) генеративный novel-view (`ViewSynthesizer`) как render-adapter (шов A) и как pre-reconstruction амплификатор (шов B) — границы применимости, где он НЕ используется (редактирование / произвольная камера).**
2. **Каноническая модель сцены.** Точно опиши data-model: сущности, поля, единицы, мировой фрейм, слои (`proposal`/`corrections`/`resolved`), метаданные уверенности, ссылки на рендер-ассеты **и на синтезированные ракурсы (выход ViewSynthesizer с их камерами)**. Типизированные стабы (`dataclasses`/`pydantic`) + набросок сериализации.
3. **Ключевые контракты** как Python ABC с docstring и type hints (без реализации): `ModelProvider` и подтипы (`Detector`, `Tracker`, `FieldCalibrator`, `PoseEstimator`/HMR, `BallTracker`, `EnvReconstructor`, `AvatarBuilder`, **`ViewSynthesizer`**), `JobQueue`/`Worker`, `Cache`, `CorrectionEngine` (4 режима распространения), `Exporter`, `RenderPass`. Для `ViewSynthesizer` явно отрази **оба шва**: метод(ы) для генерации нового ракурса как `RenderPass`-совместимый выход (шов A) и для генерации набора ракурсов на вход реконструкции (шов B).
4. **Структура пакетов** (дерево директорий) с ответственностью и направлением зависимостей (core ← adapters; core ни от чего инфраструктурного не зависит).
5. **Потоки данных и управления.** Mermaid-диаграммы: ingestion → (опц. амплификация ViewSynthesizer шов B) → выбор эпизода → стадийные задачи → сборка сцены → цикл редактирования → рендер-пасс (3DGS/аватары **или** ViewSynthesizer шов A) → экспорт. Отдельно — механизм синхронизации прокси↔фотореал (единый SMPL-источник) и место обоих швов ViewSynthesizer.
6. **ADR** (по файлу на решение в `docs/adr/`, включая **0007 — ViewSynthesizer / генеративный novel-view**): контекст / варианты / решение / последствия.
7. **Карта риск → митигация**, привязанная к архитектуре (из ТЗ): edit↔render-синхронизация, стоимость per-subject аватаров (×24), высота мяча в моно, дрейф гомографии, неблокирующий UI, **ограничение фрустумов ViewSynthesizer (R-14), пиксели-не-геометрия (R-15), толпа/дрейф идентичности (R-16)**.
8. **План реализации по милстоунам** (M1 редактируемый цикл → M2 фотореал + ViewSynthesizer шов A → M3 качество + ViewSynthesizer шов B); **вертикальный срез M1** с работающим артефактом на одном клипе.
9. **Каркас репозитория.** Дерево директорий, стаб-файлы интерфейсов, заполненные ADR, README, `pyproject.toml` с **запиненными** зависимостями (+ пометки AGPL/GPL/SMPL), `justfile`/`Makefile`. **Только заглушки** (`raise NotImplementedError` + docstring).

## 3. Как работать (требования к процессу)

- **Гексагональность строго.** Чистое ядро без `bpy` и без ML/рендер-зависимостей. Blender и каждая модель (включая `ViewSynthesizer`) — за адаптерами. Зависимости направлены внутрь.
- **Тестируемость без GPU/Blender.** Реализуй **фейковые адаптеры** (`FakeDetector`, `FakeTracker`, `FakeHMR`, `FakeBallTracker`, `FakeEnvReconstructor`, `FakeAvatarBuilder`, `FakeRenderPass`, **`FakeViewSynthesizer`**) и один сквозной «dry-run» от источника до экспорта. `FakeViewSynthesizer` должен покрывать оба шва (вернуть «видео»-заглушку для A и набор фейковых ракурсов для B). Ядро проходит `pytest` **зелёным без GPU и без Blender**.
- **Движок коррекций — честная математика.** 4 режима распространения (`constant offset`, `interp between keys`, `re-fit` через инъектируемый порт, `temporal smoothing`) как чистые функции над SMPL/кривыми, с тестами.
- **Решай, не спрашивай.** Где неоднозначно — дефолт + запись в ADR. В конце — список допущений.
- **Не реализовывать тяжёлое.** Никаких реальных детекторов/HMR/сплаттинга/video-diffusion/`bpy`-операторов в теле — только контракты, типы, scaffolding, фейки. Заглушки честные (`NotImplementedError` + docstring).

```
    adr/0007-view-synthesizer-novel-view.md   # video-diffusion: швы A и B, границы применимости
    risk-map.md
    roadmap.md              # M0..M3 → пакеты/тикеты, вертикальный срез M1

      scene/                # типы сцены, слои, единицы, фрейм, синтез-ракурсы, сериализация

    adapters/
      models/               # стабы реальных моделей за портами (NotImplementedError)
      viewsynth/            # адаптеры ViewSynthesizer (ReCamMaster/TrajectoryCrafter/GEN3C/...) — стабы, оба шва
      blender/              # адаптер Blender (bpy) — изолирован, стабы
      render/               # рендер-пасс: сплаты/аватары + ViewSynthesizer-шов-A — стабы
      export/               # glTF/USD/FBX/Alembic/JSON, three.js — стабы
      fakes/                # фейковые адаптеры (вкл. FakeViewSynthesizer, оба шва)
    app/                    # сборка/композиция (wiring), CLI dry-run
  tests/                    # тесты ядра на фейках (без GPU/Blender)
```

## 5. Definition of Done

- `docs/architecture.md` (обзор + диаграммы, оба шва ViewSynthesizer), `docs/scene-schema.md`, `docs/adr/*.md` (включая 0007), `docs/risk-map.md`, `docs/roadmap.md`.
- `src/` с деревом пакетов, ABC-стабами портов (вкл. `ViewSynthesizer`), типизированной моделью сцены, реализацией движка коррекций, фейковыми адаптерами (вкл. `FakeViewSynthesizer`).
- `tests/` для ядра на фейках — **зелёные, без GPU/Blender**.
- Сквозной CLI «dry-run»: источник → (опц. амплификация шов B на фейке) → стадии (фейки) → сцена → правка → перенос правки → рендер (FakeRenderPass **или** FakeViewSynthesizer шов A) → экспорт, отрабатывает end-to-end.
- `pyproject.toml` (запинено, пометки лицензий), `README.md`, `justfile`.
- Финальный отчёт: **какие решения принял и почему / допущения / открытые вопросы / следующие шаги (вход в M1)**.

## 6. Чего НЕ делать

- Не реализовывать мульти-вью реальных камер (только шов: камеры — список, гомография как частный случай калибровки). Примечание: ViewSynthesizer-«амплификатор» (шов B) использует тот же мультивью-вход — синтетическими ракурсами.
- Не импортировать `bpy` или ML/рендер/video-diffusion-библиотеки в `core/`.
- Не делать реальный инференс/сплаттинг/генеративный novel-view/`bpy`-операции — только контракты, типы, scaffolding, фейки.
- Не использовать `ViewSynthesizer` там, где нужны редактирование (поз/траекторий) или произвольная свободная камера — зафиксируй это ограничение в ADR 0007.
- Не воспроизводить защищённый авторским правом вещательный контент; использование — внутреннее/исследовательское.
- Не «прятать» нерешённые решения — фиксируй их в ADR.
